    { moduleComment = Just " Reclaim pressure demo: build a list, then deep-clone it many
         times, walking and discarding each clone.

         The structure is opt-resistant in the strict sense:
           * 'sumList cloned' depends on every cell of the final clone, so
             'cloneN' cannot be elided — its result is what main prints.
           * 'clone' walks every cell of its input and allocates a fresh
             ICons for each, so the optimiser cannot fold it to a no-op
             (the result is structurally distinct, even if value-equal).
           * Every intermediate clone becomes unreferenced once the next
             'clone' returns, so any working reclaim mechanism must drop
             it; without one the cells stay in the heap forever.

         With 'cloneN 3000 (repeat 100000 1)':
           * Cumulative allocation: 3000 × 100 000 cells × ~24 bytes each
             ≈ 7 GiB.
           * Steady-state live set: at most ~2 lists, ~5 MiB.

         Steady-state peak RSS observed:
           * JVM / CLR / JS reclaim via host GC.
           * LLVM reclaims via compiler-emitted refcount over libc
             malloc/free (one of `__free_recursive`'s cascading paths
             returns each ICons cell to the freelist after its clone goes
             out of scope).
           * WASM reclaims via compiler-emitted refcount over the per-
             size-bin freelist in linear memory; cumulative allocation
             never crosses the wasm32 4 GiB cap because the same bin
             blocks are reused. "
